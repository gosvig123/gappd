# Backend platform fit for explicit meeting sync

## Summary

All three candidates can support an optional cloud copy while SQLite remains authoritative on each Mac, but they place the synchronization boundary differently. Supabase bundles Apple-capable authentication, PostgreSQL, Row Level Security (RLS), migrations, policy testing, and hosted logs. A thin Go service with managed PostgreSQL exposes the same explicit push/pull boundary with greater portability and control, while making Gappd responsible for identity verification, authorization, deployment, database operations, and observability. CloudKit supplies Apple-account private databases, record-zone change tokens, subscriptions, conflict policies, and a dashboard, but requires a native CloudKit bridge and Apple-specific schema and identity semantics.

This research does not select a platform. The product decisions still needed are whether Gappd wants an app-owned account/session, whether non-Apple clients are plausible, how much server code and operations Gappd will own, and whether the service must expose an inspectable HTTP contract independent of Apple frameworks.

## Findings

### Gappd persistence boundary

- `internal/config/config.go` requires a filesystem `db_path`; `cmd/gappd/main.go` opens and initializes that store for every command. `internal/db/db.go` is a concrete `database/sql` wrapper over `modernc.org/sqlite`, enables WAL, runs SQLite-specific migrations, and rebuilds FTS5. A remote PostgreSQL or CloudKit replacement is therefore not a drop-in driver change.
- `internal/db/schema.sql` mixes durable meeting content with device-local lifecycle fields: processing claims, capture/processing failures, FTS5 triggers, and `audio_path`. `internal/meetinglifecycle/module.go` writes a local session directory into `audio_path`. An explicit cloud projection must exclude machine-local ownership and filesystem state.
- IDs are already UUID-shaped strings generated locally, which is compatible with client-originated idempotency keys. The schema lacks a general `updated_at`, deletion tombstone, server version, sync cursor, or outbox.
- Electron currently invokes the Go binary through a typed JSON command protocol (`desktop/src/main/app-protocol.ts`). `internal/appprotocol/meetings.go` exposes title, transcript, summary, segments, and limited diarization, but omits tags, language, extraction JSON, raw diarization JSON, revisions, and audio path. A sync contract should be a new deliberate boundary rather than reusing the current presentation DTO unchanged.
- Consequently, every candidate still needs local outbox/inbox state, eligibility rules, version/conflict semantics, tombstones, retry/idempotency behavior, and a projection from SQLite rows to cloud records.

### Supabase Auth + PostgreSQL + thin service

- Supabase Auth supports Sign in with Apple for web-based applications and native Apple platforms. Its OAuth flow returns an access and refresh token; native Sign in with Apple can exchange an Apple identity token. Supabase recommends native Authentication Services for native Apple apps. Web OAuth requires an Apple Services ID and rotating the Apple client secret every six months; native-only identity-token exchange avoids that specific rotation requirement ([Supabase Apple login](https://supabase.com/docs/guides/auth/social-login/auth-apple)).
- PostgreSQL RLS can restrict each operation by authenticated user. Supabase warns that exposed tables need both least-privilege grants and RLS policies, that the service role bypasses RLS and must remain server-side, and that policies should be tested for each operation ([Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security); [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).
- An explicit thin service can verify the Supabase session and own `push`, `pull`, and account-deletion transactions while PostgreSQL RLS remains defense in depth. Direct desktop access through Supabase's generated API is possible, but it would move protocol and authorization behavior into grants, policies, and database functions instead of the requested inspectable server boundary.
- Supabase supports version-controlled SQL migrations, a local stack, seeded resets, local Auth configuration, and pgTAP RLS tests. Supabase notes its local environment is not feature-complete relative to hosted projects ([database migrations](https://supabase.com/docs/guides/local-development/database-migrations); [RLS testing](https://supabase.com/docs/guides/database/postgres/row-level-security#test-your-policies)).
- Hosted projects provide Auth, API, function, and PostgreSQL logs through Logs Explorer; retention depends on plan. Query auditing requires explicit pgAudit configuration ([Supabase logging](https://supabase.com/docs/guides/monitoring-and-debugging/logs)).
- Data and migrations remain PostgreSQL-shaped, but `auth.uid()`, Supabase JWT conventions, hosted Auth, and Logs Explorer are platform coupling. Supabase can be self-hosted, but its own documentation assigns provisioning, hardening, PostgreSQL maintenance, high availability, backups, monitoring, and uptime to the operator, and notes several hosted features are unavailable ([Supabase self-hosting](https://supabase.com/docs/guides/self-hosting)).

### Thin Go service + managed PostgreSQL

- Go's standard `database/sql` provides a concurrent connection pool and transaction API; `net/http/httptest` supports isolated handler and end-to-end HTTP tests. This fits a small service that atomically accepts idempotent pushes and emits cursor-based pulls without sharing the desktop's SQLite implementation ([Go connection management](https://go.dev/doc/database/manage-connections); [Go transactions](https://go.dev/doc/database/execute-transactions); [httptest](https://pkg.go.dev/net/http/httptest)).
- PostgreSQL RLS is provider-independent and defaults to denying normal access after RLS is enabled when no policy exists. Table owners, superusers, and `BYPASSRLS` roles normally bypass it, so a service must use deliberately scoped roles and test ownership behavior ([PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).
- A managed deployment still requires separate choices for Apple identity-token verification/session issuance, schema migration tooling, secret rotation, backup/restore objectives, regional placement, and incident response. The benefit is that these choices remain behind Gappd's HTTP contract and can change without changing the desktop protocol.
- As one representative managed stack, Cloud Run accepts a Go container and terminates TLS, while Cloud SQL manages PostgreSQL. Connecting them requires service identities/IAM, regional and network choices, connection configuration, and pool limits; Cloud Run automatically captures request, container, and system logs ([Cloud SQL from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run); [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract); [Cloud Run logging](https://docs.cloud.google.com/run/docs/logging)). Other managed providers differ, so these are workload facts, not a provider recommendation.
- This option has the lowest data-plane lock-in when it uses ordinary PostgreSQL migrations and a standard HTTP/JSON contract. It has the highest app-owned code and operational surface of the three candidates.

### Apple CloudKit bridge

- CloudKit gives every container one public database plus a private database for each iCloud user. Saving private records requires the device user to be signed into iCloud. This is Apple/iCloud account state, not an app-owned Sign in with Apple OAuth session ([CloudKit database design](https://developer.apple.com/documentation/cloudkit/designing-and-creating-a-cloudkit-database)).
- Private custom record zones support opaque server change tokens and subscriptions. Clients fetch only changes after a cached token, including deletions, and process batches. This supplies pull primitives similar to a sync cursor ([CKFetchRecordZoneChangesOperation](https://developer.apple.com/documentation/cloudkit/ckfetchrecordzonechangesoperation)).
- `CKModifyRecordsOperation` supports batched saves/deletes, atomic operations within a zone, and save policies that either detect newer server versions or overwrite wholly/partially. CloudKit may reject large operations, requiring smaller batches ([CKModifyRecordsOperation](https://developer.apple.com/documentation/cloudkit/ckmodifyrecordsoperation)).
- Gappd's Electron/Go processes do not currently have a CloudKit boundary. Native private-database access would require a signed Swift helper or other native bridge plus iCloud/CloudKit entitlements. Apple's CloudKit Web Services documentation allows user-authenticated API-token access, but its server-to-server key is documented for the public database, so it does not eliminate the per-user/private-database integration problem ([CloudKit Web Services](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/SettingUpWebServices.html)).
- CloudKit Console can inspect development data, schemas, logs, and metrics. Development environments can be reset, then additive schema changes are deployed to production. Production record types and fields cannot be deleted, increasing schema lock-in ([CloudKit database management](https://developer.apple.com/documentation/cloudkit/managing-icloud-containers-with-cloudkit-database-app); [schema deployment](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema)).
- CloudKit reduces custom database and authentication infrastructure, but tightly couples identity, client implementation, schema, conflict APIs, diagnostics, and future platform reach to Apple. It also provides no app-owned HTTP server code unless Gappd adds a separate service, which weakens its fit when inspectable server/client interaction is itself a requirement.

### Decision-relevant comparison

| Concern | Supabase + thin service | Go + managed PostgreSQL | CloudKit bridge |
|---|---|---|---|
| Apple identity | Built-in provider; OAuth or native token exchange | Gappd integrates and verifies Apple identity, then owns sessions | Implicit iCloud account for private DB; not the same account model |
| Authorization | Service checks plus PostgreSQL grants/RLS | Fully app-owned checks; optional provider-independent RLS | Private database isolation and CloudKit permissions |
| Local-first support | Gappd builds outbox/cursor protocol | Gappd builds outbox/cursor protocol | Native change tokens/subscriptions/conflict policies; mapping still required |
| Server code visibility | Thin service is explicit; managed Auth/data plane underneath | Entire HTTP and transaction boundary is explicit | Native framework calls; no app-owned server unless separately added |
| Testing | Local stack, migrations, pgTAP; hosted differences remain | `httptest` plus PostgreSQL integration tests; test infrastructure is app-owned | Development environment and console; local-emulator support not established here |
| Observability | Hosted multi-service logs; plan-dependent retention | Provider logs/metrics plus app-defined traces | Container logs/metrics; less app-owned server instrumentation |
| Operational burden | Lowest if hosted; rises sharply if self-hosted | Highest: service, auth, migrations, DB, backups, deployment | Lowest server operations; Apple entitlement/schema operations remain |
| Lock-in | PostgreSQL portable; Auth/RLS helpers and platform services coupled | Lowest with standard HTTP and PostgreSQL | Highest Apple platform, identity, framework, and additive schema coupling |

## Gaps

- The separate Apple-authentication research ticket should determine whether Gappd will use native Authentication Services, OAuth with a custom URL callback, or CloudKit account state; this materially changes the bridge and token lifecycle.
- No expected user count, transcript volume, retention period, region, recovery objective, or operating budget exists, so cost and capacity cannot be compared responsibly.
- A concrete managed PostgreSQL provider has not been selected; Cloud Run/Cloud SQL is only a representative operational model.
- CloudKit local-emulator and automated private-database test capabilities were not established from the reviewed primary sources.
- Current documentation was fetched on 2026-08-20. Hosted product plans, log retention, Apple entitlement requirements, and deployment tooling should be rechecked during platform selection.
